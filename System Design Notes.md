- Clarify use case (search engine?), storage time/limit, accuracy (chance of bloom filter false positive), Global? Robots.txt?
- High level: Seed URLs -> Queue -> Crawler Pool -> Download Content -> Add more URLs to Queue -> Save Downloaded URL in DB
- Account for politeness. Scale out queue to multiple and use circular hashing to map domain to one queue. Crawler only subscribes to one queue to ensure a domain is only processed by one at a time. This could rely on Kafka consumer group guarantee.
- Account for robots.txt. Download from root and store in crawler memory. Check if URL is in disallow list before downloading or adding to queue. For back off rules, we could choose to add rate limiter service to account for it, though not completely necessary given existing politeness queueing.
- Visited URLs optimization. We can add hashing by URL in a centralized cache like Redis. This would need to be partitioned to support the scale and hash by domain. The downside is the size needed to store hash of all the URLs. Another approach is to use a bloom filter. The bloom filter can be centralized as well which helps save space, but that adds network hop. Another way is to keep bloom filter local and either pubsub with other nodes for bit updates or hash domain to crawler node so that it can maintain local bloom filter. Another way is to colocate the redis node with the crawler node. To have 100% accuracy and still leverage bloom filter, we can do two phase approach. If bloom filter returns negative, crawl immediately. If it returns positive which could be false positive, then check Redis.
- DNS can be cached to save time on DNS resolution
- A front queue set can be added to further prioritize URLs based on page rank and other factors. It is assigned to a ranked queue based on priority. Then a consumer uses weighted round robin to place these in the back queue which is hashed by domain that gets consumed by crawlers.
